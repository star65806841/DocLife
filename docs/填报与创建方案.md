## 0. 背景

项目树本质是「表格的分类 + 打印顺序」。当前已经具备：树结构、自由拖拽、表格填报、格式工具栏、保存/重开一致。
下一步要把「建工程」和「填表」从手工操作升级为**规则驱动**，减少重复劳动并保证一致性。

依据文件：根目录 `3-单位分部分项划分规则.doc`（JTG F80/1-2017 划分规定，WPS 保存的 Word 97 格式）。

## 1. 现状盘点

### 1.1 节点类型与层级规则

定义在 `src/model/custommodel/nodetyperegistry.cpp` 的 `allowedChildTypes` 矩阵：

| 父节点 | 允许的子节点 |
|---|---|
| project（工程根） | unit、folder、sheet |
| unit（单位工程） | sub、folder、sheet |
| sub（分部工程） | item、folder、sheet |
| item（分项工程） | folder、sheet |
| folder（目录） | folder、sheet |
| sheet（表格） | 无（叶子） |

- 单位/分部/分项只出现在唯一父级下，因此只能同级排序；目录/表格可自由换父级。
- 拖拽规则由 `ProjectTreeModel::canDropMimeData` 与 `ProjectContext::moveNode` 统一校验。

### 1.2 数据模型（工程库 `.dlf`，SQLite）

| 表 | 用途 |
|---|---|
| `project_info` | 工程名、工程编号、建设/施工/设计/监理单位 |
| `tree_nodes` | 树节点（id/parent_id/type/name/sort_order/attrs） |
| `project_sheets` | 工程内的表实例（模板标题、行列数） |
| `sheet_cells` | 单元格样式与模板文本（字体、颜色、对齐、合并、边框） |
| `form_values` | 用户填写的单元格文本 |
| `sheet_row_heights` / `sheet_col_widths` | 行高列宽 |

模板库 `.dlt` 结构：`catalogs / folders / templates / template_sheets / sheet_cells / process_rules`。

### 1.3 现有数据事实（`resources/data/examples.dlt`）

- 77 张表，33,123 个单元格；
- **`bg_color` 全部是 `#FFFFFF`**：颜色语义完全没被占用；
- `h_align`：左 21,641 / 中 11,029 / 右 453；
- `v_align`：几乎全部居中（33,122）；
- `font_color`：黑色 33,098，红色 25；
- 工序规则 337 条 / 38 类：`process_rules(process_name, sheet_code, sheet_title)`，可与 `template_sheets` 关联。

### 1.4 现有创建与填报流程

- 创建：右键菜单直接 `addChild`，名字取类型默认标签（"单位工程"），**没有任何参数输入**。
- `NodeAttributes` 已预留 `startLinear / endLinear` 字段（未使用）。
- 填报：文本写 `form_values`，格式写 `sheet_cells`，保存工程时统一落库。
- 打开填报：右键项当前被暂时注释（提交 `9515454`）。

## 2. 议题一：单位/分部/分项的确定性创建

### 2.1 规则来源

JTG F80/1-2017 的划分是**确定性**的，按工程类别给参数即可推导：

| 层级 | 划分依据（示例） |
|---|---|
| 单位工程 | 路基/路面：每 10km 或每合同段；桥梁：每座（分幅按单幅）；隧道：每座（双洞按单洞） |
| 分部工程 | 路基/路面：1–3km 段；桥梁：每墩台 / 每 1–3 跨或联；隧道：洞口每处、洞身每 ≤200m、路面 1–3km |
| 分项工程 | 固定清单（如土方路基、填石路基、软土地基处治…） |

### 2.2 方案：把规则做成数据 + 创建向导

1. **划分模板元数据**（建议放模板库或独立 JSON，按工程类别组织）：
   ```json
   {
     "category": "roadbed",
     "unitRule":  { "type": "length", "stepKm": 10, "byContract": true },
     "subRule":   { "type": "length", "stepKm": 3, "splitByDirection": true },
     "itemCatalog": ["土方路基", "填石路基", "软土地基处治", "土工合成材料处治层"],
     "itemTableMap": { "土方路基": ["LJJ1", "LJJ2"] }
   }
   ```
   分项清单可直接从 `process_rules` 的 38 类工序反向生成，减少手工维护。

2. **创建向导（4 步）**：工程类别 → 范围（合同段、起止桩号、长度）→ 结构物参数（桥：跨数；隧道：单/双洞）→ **预览生成的树** → 确认。

3. **节点落库**：`attrs` 增加 `code`（如 `LJ-01`）、`category`、`ruleId`、`startLinear/endLinear`；名称自动拼装（"路基工程 K0+000～K10+000"）。

4. **可重复执行**：同参数再跑一次是「补齐/重建」，只增不删；已填表格保留；冲突按 `code` 或桩号区间检测。

5. **自动挂表**：创建分项时按 `process_rules` 自动挂推荐表（`AddSheetDialog` 的「按工序」已有雏形）。

### 2.3 待决策

- 10km / 1–3km 是固定值还是可配置？
- 分项清单是硬编码在文档里读，还是做成可维护的数据表？
- 命名规则是否带桩号？编码规则？

## 3. 议题二：单元格角色（只读 / 项目信息 / 用户填写）

### 3.1 原则

**不要用颜色当数据**。给单元格加 `role` 列，颜色只是生成模板时的标记手段和编辑时的视觉提示。

| role | 含义 | 默认底色 | 编辑 |
|---|---|---|---|
| `title` | 表名/标题 | 白 | 只读 |
| `readonly` | 固定说明文字 | 淡灰 `#D9D9D9`（RGB 217,217,217） | 双击弹窗确认后解锁 |
| `project` | 工程信息（建设单位等） | 淡黄 `#FFF2CC`（RGB 255,242,204） | 由项目信息自动填充，可刷新 |
| `input` | 用户填写 | 白 | 可编辑 |
| `summary` | 汇总/评价结果 | 淡蓝 `#DDEBF7`（RGB 221,235,247） | 只读（由计算写入） |

### 3.2 行为

- **只读解锁**：双击 → 确认弹窗 → 解锁；解锁状态只记在工程侧（`cell_locks` 表或节点 attrs），不改模板；支持「恢复锁定」。
- **项目信息**：`role=project` 的格子带 `field_key`（`projectName / ownerUnit / constructionUnit / designUnit / supervisionUnit`）。建表时按 `ProjectInfoModel` 自动写入 `form_values`。
- **同步提醒**：比较「表格里的工程信息」与「当前工程信息」，不一致时在「刷新项目信息」按钮上用 `fluent::status_info::Avatar` 加红点/角标提示；点击后全表重填（覆盖前提示）。
- **冲突**：角色色是默认层，用户手动填充覆盖它；工具栏「无填充」= 回落到角色色。

### 3.3 模板标记方式

在生成模板的 Excel 里用固定填充色标记，生成器翻译成 `role/region` 后**把颜色清回白色**：

| 标记色 | 含义 |
|---|---|
| `#D9D9D9`（RGB 217,217,217） | 只读 |
| `#FFF2CC`（RGB 255,242,204） | 项目信息 |
| `#DDEBF7`（RGB 221,235,247） | 汇总 |
| 白色 | 用户填写 |

不想在 Excel 里涂色时，也可以用一个隐藏 sheet 写区域矩形（如 `A1:D3 = title`）。

## 4. 议题三：区域与默认对齐

- 现状已有 `h_align/v_align`，但缺少「区域」概念。
- 建议 `region ∈ {title, project, body, summary, sign}`，每个 region 固定默认对齐：
  标题居中、项目信息左、内容居中、汇总居中、签字左。
- **生成模板时**就按区域写入 `h_align/v_align`，运行时不再判断，避免每次打开重算。
- 区域与角色正交：同一个 `body` 区域里可以既有 `readonly` 也有 `input`。

## 5. 议题四：自动评价与汇总

难点：`form_values` 是纯文本，没有语义。分三步：

1. **字段化（先做）**：模板标记「检测项行」，定义列语义（项目名称 / 允许偏差 / 实测值 1..n / 合格判定）；运行时逐行算合格与否、合格率，写回 `summary` 单元格。
2. **评定规则**：按 JTG F80/1-2017（主控项目 100% 合格 + 一般项目合格率阈值）做成可配置规则，输出「合格/不合格」与汇总。
3. **公式引擎（最后）**：只读公式子集（SUM/COUNT/AVERAGE/IF/ROUND），汇总格存公式而非值；兼容性是主要风险。

待提供：1–2 张典型表的汇总逻辑（参与列、判定阈值）。

## 6. 议题五：补充建议

- **打印/目录编号**：树顺序即打印顺序，自动生成 `01 / 01-02` 编号，拖动或改名后重排。
- **模板版本与升级**：模板更新后已建项目只提示差异，不自动改已填内容。
- **表状态机**：草稿 → 填报中 → 已审核（审核后整表只读），比逐格锁定更好用。
- **必填校验 / 签字栏**：与 role 联动，签字区必须手填。
- **自动保存 / 崩溃恢复**：目前只在保存时落库，编辑中崩溃会丢。
- **多模板集合**：划分规则也要能按集合选择（现在是写死的 `examples`）。

## 7. 数据模型变更草案

```sql
-- 模板库与工程库共用
ALTER TABLE sheet_cells ADD COLUMN cell_role TEXT;   -- title/readonly/project/input/summary
ALTER TABLE sheet_cells ADD COLUMN region TEXT;      -- title/project/body/summary/sign
ALTER TABLE sheet_cells ADD COLUMN field_key TEXT;   -- projectName / ownerUnit / 检测项名称

-- 工程库：只读解锁状态（也可放 tree_nodes.attrs）
CREATE TABLE IF NOT EXISTS cell_locks (
    sheet_id INTEGER, row INTEGER, col INTEGER, unlocked INTEGER,
    PRIMARY KEY (sheet_id, row, col)
);
```

生成器（Excel → `.dlt`）需要同步升级：读取标记色/隐藏 sheet，写 `cell_role/region/field_key`，并把颜色清回 `#FFFFFF`。
